# Product Planning

Use this skill when clarifying product direction, MVP scope, release gates, customer validation, or Linear work structure.

## Principles

- Be a thought partner, not a ticket factory: understand the user problem and uncertainty before adding work.
- Default to the smallest coherent product cut that demonstrates the promised end-to-end value.
- Treat user evidence and implementation readiness as separate questions. Keep evidence claims bounded by what was observed.
- Record decisions and unresolved assumptions in durable product context and Linear issues.
- Use the repo-owned `linear` CLI for all Linear reads and mutations; see `linear-cli`.

## Match the operating mode

Before proposing schedules, owners, or parallel work, establish how the user wants to operate. For a personal or side project:

- Do not add due dates, deadlines, calendar timeboxes, owner assignments, or coordination overhead unless explicitly requested.
- Prefer a founder-led sequence: finish a cohesive demo-ready product cut, then use recorded demos and organic outreach one conversation or trial at a time.
- Do not create prospect quotas or parallel recruitment campaigns by default.
- Keep technical readiness gates distinct from external recruitment and validation. Do not make recruitment a pre-build task when the user wants to build first.
- Preserve useful evidence criteria where the user has chosen them, but report sparse evidence as directional or inconclusive rather than creating pressure to hit a date.

For team-led work, ask before assuming a calendar plan or parallel ownership structure; add those only when they support the user's stated constraints.

## Planning dialogue

- Present one consequential decision at a time, with the relevant context, tradeoffs, and a recommendation.
- Ask only for choices that materially affect scope or sequencing; do not reopen decisions already made.
- Keep Linear issues bounded and actionable. Use dependencies to represent real sequencing, not to imply a schedule.
- Avoid prospect-count, study-duration, or launch-date commitments unless the user requests them or explicitly accepts an evidence protocol containing them.
- Keep the product mission concise; use a release-plan document for detailed milestone scope and acceptance criteria.
