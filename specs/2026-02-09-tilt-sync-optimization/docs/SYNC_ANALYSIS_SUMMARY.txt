KEY FINDINGS
================================================================================

1. CURRENT PROBLEM: File changes sync entire monorepo to every service
   - sync(PROJECT_ROOT, '/app') copies 40,000+ files on each change
   - Unrelated app changes (capture) restart unrelated services (api-server)
   - Services rebuild unnecessarily on ANY monorepo-wide event

2. ROOT CAUSES (5 Critical Issues):
   
   a) DOCKER TARGET MISMATCH
      Current:  target="build-all"     (builds entire monorepo)
      Should be: target="api-server"    (builds only api-server + deps)
      Impact:   Initial builds 40-60% slower than needed
   
   b) MONOREPO-WIDE FALLBACK TRIGGERS
      Current:  fall_back_on(['pnpm-lock.yaml', ...])
      Problem:  pnpm-lock.yaml is global; ANY package change triggers rebuild
      Impact:   Capture dependency change → all 3 services restart
   
   c) OVERLY BROAD PROJECT SYNC
      Current:  sync(PROJECT_ROOT, '/app')
      Problem:  Syncs capture changes to api-server container unnecessarily
      Impact:   5-10x slower file syncs, network overhead
   
   d) INSUFFICIENT IGNORE PATTERNS
      Current:  ignore=['infra', 'dist', 'build', 'node_modules']
      Missing:  Test files, storybook, docs, other apps
      Impact:   Test changes trigger rebuilds (should not)
   
   e) NO DEPENDENCY DISTINCTION
      Current:  deps: [^:build] in moon.yml rebuilds ALL packages
      Problem:  Doesn't distinguish between direct deps and transitive
      Impact:   Unrelated package changes cause rebuilds

KEY INSIGHTS
================================================================================

1. Tilt watches directories broadly; file patterns narrow the scope
   - docker_build('api-server', PROJECT_ROOT) means "watch PROJECT_ROOT"
   - ignore patterns tell Tilt what NOT to watch
   - More specific ignore patterns = fewer false positives

2. Fall_back_on is expensive; minimize trigger conditions
   - Monorepo-wide pnpm-lock.yaml is a bad trigger
   - Should only watch direct dependency package.json files
   - Limits cascading restarts to actually affected services

3. Sync scope should match service scope
   - api-server only needs apis/api-server/src and packages/
   - Syncing entire PROJECT_ROOT is wasteful
   - Smaller syncs = faster feedback

4. Docker multi-stage targets are powerful but underutilized
   - Dockerfile defines separate targets for each app
   - Tiltfile should use app-specific targets, not build-all
   - Matches the monorepo's actual build graph

5. Moon's build graph has more granularity than currently utilized
   - Could optimize ^:build to understand direct vs transitive deps
   - Future improvement opportunity

================================================================================
KNOWN LIMITATIONS
================================================================================

1. LOCKFILE CASCADE NOT RESOLVED
   pnpm-lock.yaml is monorepo-wide and remains in fall_back_on for all
   services. Any pnpm add in any app still triggers full rebuilds for all
   running services. Isolating lockfile changes requires app-specific lock
   fragments or removing pnpm-lock.yaml from fall_back_on.

2. BROAD PACKAGES/ SYNC
   sync(packages, '/app/packages') syncs ALL packages to every service.
   Changes to unrelated packages still trigger sync I/O. To fully isolate,
   sync only computed dependency packages.

3. DOCKERFILE TARGETS
   The Dockerfile must have workspace and admin targets added before those
   Tiltfiles can use app-specific targets.
